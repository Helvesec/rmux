# RMUX 0.11.0 release notes

These notes describe the 0.11.0 release scope and its known limitations.
The published release records its exact source SHA and qualification run under
[Candidate reference](#candidate-reference); these notes alone do not certify
package availability or completed native qualification.

## Breaking upgrade: restart the daemon

0.10.0 (wire 8) and 0.11.0 (wire 9) cannot exchange ordinary RPC frames.
There is no overlapping compatibility range: the
[frame envelope](../../crates/rmux-proto/src/envelope.rs) accepts only its own
wire version. Installing a new client does not upgrade an already running
daemon. You must restart the daemon before using the new client with it.

**Open sessions are lost when the old daemon stops.** Attached clients disconnect;
running processes in panes cannot be recovered by reattaching. Save application
work, configuration, commands and useful terminal output before stopping it.
A text capture is not a process checkpoint. Detaching a client is not a backup.
Follow the [0.10 → 0.11 migration guide](../../docs/migration/0.10-to-0.11.md), including
the separate steps for every named socket or endpoint you use.

The [CLI incompatibility diagnostic](../../src/cli/error.rs) requests a daemon
stop followed by a retry. This does not make mixed client/daemon operation
supported, and a shutdown command is not a session migration mechanism.

## SDK pane-state subscriptions

Consumers must handle both `PaneStateEvent::Exited` and `PaneStateEvent::Closed`
as terminal events. With `sdk.pane.state_events.exit` negotiated, process exits
use `Exited`, including when the daemon keeps the dead pane. The event carries
the exit status or signal when available. Other closures still use `Closed`,
as do wire 9 connections without this capability.

## Ratatui applications

`ratatui-rmux` 0.11 implements `Widget` for the Ratatui 0.30 buffer.
Applications on Ratatui 0.29 must keep `ratatui-rmux` 0.10 or upgrade their
Ratatui dependency before updating the adapter. This does not require changes
to applications that only use `rmux-sdk`.

## File-backed source input

Wire 9 adds the negotiated `SourceFileInputV1Request` message (C2S140) for
`source-file` files that use `new-pane -I`. Finished binary stdin travels
separately from source code and is consumed only after successful pane creation.
The CLI requires `commands.source_file.input_pull.v1` to pass redirected stdin.
Ordinary configuration files leave their caller's stdin available. With
`commands.source_file.input_relay.v1`, a background source command retains
access to redirected stdin after the invoking CLI exits.
A peer without `commands.source_file.input.v1` keeps the ordinary source route
without this input channel; sent offers are never replayed. Existing DTOs and
V1 payloads retain their meaning. This additive message requires no additional
restart beyond the 0.10 → 0.11 upgrade described above. See the
[protocol description](../../crates/rmux-proto/README.md#file-backed-source-input-c2s140).

## Compatibility updates

- #259: answer SIXEL capability queries when a native client enables SIXEL
  passthrough and `allow-passthrough` permits delivery; this does not add retained images.
- #261: complete command names, built-in aliases and configured aliases in the
  command prompt, with a choice menu that adjusts to terminal resizing.
- #254: support targets without native 64-bit atomics through `portable-atomic`
  and add a PowerPC Linux build and test gate; native-atomic targets keep `std` atomics.

## Scope and qualification limits

0.11 is a pre-1.0 release. There is no audited SemVer 1.0 contract for the CLI,
wire protocol or Rust SDK. Compatibility work on tmux commands, options and
control mode must be described against the final candidate's actual test
results; these notes do not declare full tmux parity.

The qualification target is macOS Apple Silicon, Linux x86_64 and Windows 11
x64, including installed-artifact smokes and a 24-hour soak. See the linked qualification run for results on the released build. macOS Intel and Linux arm64 are additional hosted
build/smoke targets in the [release workflow](../../.github/workflows/release.yml);
that definition alone proves neither completed runs nor native qualification.
Windows 10 is not qualified;
Windows 11 results do not qualify Windows 10.

No performance claim is made for 0.11. There is no qualified performance table
or claim that RMUX is faster than tmux in these release notes.
Any future measured table must be attached to the release as a campaign artifact
outside the qualified source content, with its source SHA and raw measurements,
under the [benchmark artifact policy](../../docs/benchmarks.md).

0.11 does not reduce the source size. The
[source inventory](../../scripts/source-inventory/README.md) measures 364,547
handwritten production lines in 0.11.0. The development plan's target G was
301,947 lines: 0.11 misses it by 62,600 lines, and the target is deferred to 0.12.
CI checks the [source budget](../../scripts/source-inventory/budgets.json), which records
a ratchet of 362,622 lines and a growth envelope of 1,925 lines for this release. The reduction toward G is planned for 0.12.

The following limits apply:

- Kitty Keyboard is disabled by default in the inspected source, as detailed
  under [Candidate reference](#candidate-reference). The complete native keyboard
  matrix is deferred. An opt-in build is not a qualified feature, and the final
  package's feature selection still needs verification.
- Landed floating panes and their SDK, Ratatui and Web projections are
  experimental; their complete behavior matrix is deferred.
- Web sharing is experimental. Qualification beyond loopback is deferred;
  default loopback binding is not proof that remote exposure is qualified.
  See the [Web sharing guide](../../docs/web-share.md) for the existing security model.
- Native IME is not qualified. OSC 52, cursor shape, SIXEL passthrough and
  Kitty graphics lack the complete native matrix. The bounded Windows 11 SIXEL
  result below does not qualify other terminals or retained-image support.
- On Unix, OSC 7501 foreground attribution remains heuristic (variant B).
  A complete old-program report still queued in the PTY when its successor
  takes the foreground can be attributed to the successor. The first report
  from the new program is preserved without a capability query. An incorrectly
  attributed active report has no heartbeat timeout; this defect remains open.
  See [program status lifetime and bounds](../../docs/program-status.md#lifetime-and-bounds).
- Session persistence through resurrect or continuum is not guaranteed.
  Layout exports do not preserve live processes across this upgrade.

## Downloads, channels and signatures

The intended primary delivery formats are tar and ZIP archives with their
`install.sh` and `install.ps1`, deb, rpm, the Homebrew tap and crates.io.
They are not confirmed available by these notes. Keep the whole archive layout,
including private helpers and bundled dependencies; copying only the public
CLI is insufficient. Use one installation channel consistently for upgrade,
rollback and removal.

WinGet, Chocolatey, homebrew-core and Scoop are subject to submission and
external acceptance. Availability is not guaranteed on release day; “submitted”
must only be reported after an actual submission. Snap and other channels must
likewise be listed from actual publication receipts, not from intended scope.
crates.io remains conditional on completing the first publication of
`rmux-bootstrap`; otherwise the crate set is deferred rather than partially
published. The [channel policy](../../.github/release/channel-policy.json)
describes automation eligibility, not a receipt proving delivery.

macOS RMUX binaries retain **ad hoc** signatures and are **not notarized**.
Gatekeeper may block a browser-downloaded executable. Prefer an available
Homebrew tap or the archive's installation script; these are not notarization.
Windows RMUX binaries are **unsigned**: no RMUX Authenticode signing is promised,
and Windows may display a trust warning. A bundled Microsoft dependency's
signature does not sign RMUX itself.

Signed release tags, SHA256SUMS, Sigstore bundles and build provenance authenticate
release source and assets; they do not replace Apple notarization or Windows
Authenticode. Verify the actual published assets with the repository's
[verification guidance](../../SECURITY.md) before installation. Final asset
verification is still required; these notes supply no attestation or checksum.

## Known Windows limitations

Native Windows 11 proofs recorded on 27 November 2026 cover #92 (multiline
OpenSSH/ConPTY paste), #211 (SIXEL passthrough), #213 (Escape in lazygit), #214
(50 startup/size checks), #218 (popup cursor visibility) and #219 (a bounded

limitations table on that evidence. The proof record is `PREUVES-WINDOWS.md`
in the release integration evidence; it was run on the earlier r18 source,
not on this assembled candidate. It does not certify the complete terminal
matrix or final release artifacts.

## Candidate reference

The release publisher appends the exact source SHA, version tag and qualification
run to these notes.

The source observations below are source inspection, not native qualification:

- [Cargo.toml](../../Cargo.toml) declares
  version 0.11.0; the [wire envelope](../../crates/rmux-proto/src/envelope.rs)
  declares wire 9 and a supported range of 9 through 9. This excludes ordinary
  wire-8 RPC; the destructive shutdown fallback is not mixed-version operation.
- The root default feature set contains `web`, not `kitty-keyboard`;
  [rmux-core](../../crates/rmux-core/Cargo.toml)
  exposes `kitty-keyboard` as an opt-in feature. The
  [fallback regression](../../crates/rmux-core/tests/kitty_fallback.rs)
  specifies no Kitty negotiation replies when that feature is absent. Its
  presence is source evidence, not a claim that this test or a terminal matrix
  has passed on the final artifacts.

For the artifact hashes, use the release’s signed `SHA256SUMS`. The qualification
run and package manifest, rather than source inspection, identify the tested bytes.
